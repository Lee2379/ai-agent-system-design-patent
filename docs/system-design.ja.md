# システム設計の分析

[ポートフォリオ](../japanese-readme.md) · [English](system-design.md) | 日本語

## 1. 設計の意図

提供された明細書は、機体群全体の運航計画、自律的な配送の実行、継続的な情報交換を結び付けています。構成の中心は、機体群を統括する**階層型エージェント**と、通信を調整する**ネットワーク型エージェント**の役割分担です。GPS、機体上のセンサー、衛星通信が配送に必要な情報と接続を提供します。

本書では、次の二つを区別します。

- **原文の設計:** 提供された明細書に記載された動作。
- **実装上の検討事項:** 動作を具体化するための技術的な提案。ポートフォリオとしての分析であり、元の発明の請求項に追加したものではありません。

## 2. 責任の境界

| 境界 | 原文の設計 | 実装上の検討事項 |
|---|---|---|
| プラットフォーム → AI制御 | 注文の受付と顧客位置の確認 | 割当前に配送先と受取地点の適合性を確認し、位置更新でミッションを変更できる条件を定義する |
| 階層型エージェント → 機体群 | 機体選択、運航計画、経路最適化 | 機体ごとに有効な割当を一つにし、経路変更にバージョンを付ける |
| ネットワーク型エージェント ↔ 関係者 | 機体、管制側、顧客の情報交換 | メッセージの順序、重複、鮮度、切断後の復旧を定義する |
| 機体センサー → 航行 | 障害物の検知と経路調整 | 機体側の判断権限、センサー状態の確認、観測が矛盾した場合の動作を定義する |
| AI制御 → 顧客 | 到着前の通知 | 到着予測の更新、再試行、重複排除、通知の到達確認を定義する |
| 運用 → 学習 | 経路、画像、センサー値の改善への利用 | データセットと候補モデルを評価してから更新する |

## 4. 情報仕様の提案

以下のフィールドは、構成要素間の境界を具体的に検討するための例です。実装済みのAPIではありません。

| 記録 | フィールド例 | 目的 |
|---|---|---|
| 配送要求 | `request_id`, `destination`, `delivery_point_id` | 注文と受取地点の対応付け |
| ミッション割当 | `mission_id`, `drone_id`, `route_version`, `issued_at` | 有効なミッションの識別と古い経路の排除 |
| テレメトリー | `mission_id`, `observed_at`, `position`, `battery_state`, `sensor_health` | 情報の鮮度と飛行継続能力の確認 |
| 到着通知 | `mission_id`, `eta`, `notification_id`, `sent_at` | 重複通知の防止と通知時刻の評価 |
| 配送記録 | `mission_id`, `outcome`, `completed_at`, `data_references` | 配送結果と保存された根拠の対応付け |

実装に先立ち、時刻源、座標系、単位、アクセス制御、スキーマ更新方法を定める必要があります。

## 5. 異常時の動作

![異常時の動作と実装条件](../assets/fig-05-safety-responses-ja.svg)

原文には、通信の冗長化、障害物回避、監視、帰還、安全な着陸が記載されています。実装では、各動作を実行できる条件を具体化します。

| 状況 | 原文との関係 | 実装上の検討事項 | 収集する根拠 |
|---|---|---|---|
| 通信断 | 冗長な通信経路、帰還・安全着陸 | 通信タイムアウトと機体側の代替動作を定義する | 切断・復旧の時系列、選択された動作 |
| 障害物の検知 | センサーと自動経路変更 | 想定環境で必要な検知・回避性能を定義する | シナリオ網羅性、介入回数、回避結果 |
| 電源異常 | 帰還・安全着陸の記述 | 低残量の閾値と制御可能な着陸条件を定義する。完全な電源喪失は別途扱う | エネルギー収支と制御された異常試験 |
| 気象変化 | 気象・環境情報による経路更新 | 経路変更、待機、中止の条件を設定する | 運用限界と判断履歴の照合 |
| 古い指示・重複した指示 | 継続的な連携 | 割当を版管理し、同じメッセージを再処理しても状態が壊れないようにする | 再送・順序逆転の試験 |
| 受取地点が利用不可 | 指定された配送先 | 受け渡し確認、中止、代替地点の手順を定義する | 地点不適合時の復旧事例 |

最後の二項目は原文で未定義の点を具体化するための提案です。提供資料に飛行安全性の検証結果は含まれていません。

## 6. セキュリティと運用データ

**原文の設計:** 衛星通信の暗号化・認証、耐量子暗号プロトコル、画像・センサー値・飛行経路の暗号化クラウド保存。

**実装上の検討事項:**

- 認証対象を明確にし、機体の鍵管理、失効、更新手順を定める。
- 具体的な暗号プロトコルを選定し、機体上の計算負荷と通信負荷を評価する。
- 測位情報や通信情報が取得できない場合、または矛盾する場合の動作を定義する。
- 顧客位置と画像へのアクセスを制限し、保存期間と削除手順を設定する。
- データセットとモデルの版を記録し、航行動作の変化を入力まで追跡できるようにする。

原文は、具体的な暗号方式、検証済みの脅威モデル、測位の完全性を確認する仕組みを指定していません。本書では、セキュリティに関する記述を設計要件として扱います。

## 7. 学習サイクル

![運用データと学習サイクル](../assets/fig-06-learning-flow-ja.svg)

**原文の設計:** 運用データを収集・保存し、航行精度、エネルギー効率、物流計画の改善に利用します。

**実装手順の提案:**

1. 飛行記録をミッション結果とセンサー状態に対応付ける。
2. 時刻、欠損、ラベル、データの出所を検証する。
3. ミッションと運用シナリオ単位で学習用・評価用データを分ける。
4. 経路、エネルギー、安全動作の基準に照らして候補モデルを評価する。
5. 承認された版を展開し、ロールバック手段と運用監視を設ける。

原文は継続的な学習を記述していますが、モデル更新の時期や展開方法を定めていません。この提案では、その境界を明確にしています。

## 8. 評価計画

以下は評価方法の提案です。ベースライン、合格基準、データセット、測定結果は提供されていません。

| 評価する点 | 指標案 | 方法 |
|---|---|---|
| 受け付けた配送の完了 | 配送成功数 / 受理したミッション数。却下・取消も別途報告 | シナリオ別シミュレーションと管理された実証 |
| 状況変化への適応 | 再計画時間、正しく再割当できた割合 | 気象、機体稼働状況、経路の変化を入力 |
| 到着通知の有用性 | 実到着時刻と通知時刻の差の分布 | 通知ログと配送記録を照合し、約5分という目標との差を確認 |
| エネルギー消費 | 配送成功1件当たりのWh。積載量・経路別に集計 | 条件を揃えたミッションの測定 |
| 通信復旧 | 切断時間、復旧時間、代替動作の結果 | 制御された切断・復旧試験 |
| 安全動作の一貫性 | 異常シナリオごとの適切な応答率 | 事前の合格基準と試験履歴を照合 |
| コスト・環境目標の達成 | 配送完了1件当たりの費用、前提を明示したエネルギー・排出量の算定 | 経路、積載量、サービス条件を揃えた比較 |

本計画の掲載は測定済みスコアを意味しません。原文のコスト削減、配送料の撤廃、環境面の利点は、運用・事業上の根拠による評価を要する目標として扱います。

## 9. 設計上の貢献

本ケーススタディは、物流の課題を、機体群の意思決定、情報交換、自律的な実行、顧客への通知、データ改善サイクルという責任に分解する設計を示しています。ここで記録する貢献は、提供された請求項と説明本文に対応する発明の考案とシステム仕様の作成です。
